# OAuth 2.1 / OpenID Connect

Expose PEZHWAN as an authorization server: register a confidential or public
client, send users through the authorization-code flow with PKCE (S256), and
let third-party apps exchange codes, refresh tokens, and machine credentials.
The OAuth surface follows the OAuth 2.1 / OIDC wire format rather than the
`{ success, data, error }` envelope. A complete example lives in
`demos/oauth-demo/`.

## Prerequisites

- A running identity server with an authenticated user (simple-auth tutorial).
- Familiarity with PKCE (RFC 7636). S256 is required for public clients.

## 1. Discover endpoints

```bash
curl http://localhost:4011/.well-known/openid-configuration
curl http://localhost:4011/.well-known/jwks.json
```

The discovery document advertises `authorization_endpoint`
(`/v1/oauth/authorize`), `token_endpoint` (`/v1/oauth/token`), `jwks_uri`, and
`code_challenge_methods_supported` (S256). It is generated by
`buildDiscoveryMetadata` (`packages/oauth/src/oidc.service.ts`).

## 2. Register a client

`POST /v1/oauth/clients` requires an `ADMIN` role. Register a web app with the
`authorization_code` + `refresh_token` grants (a public client — no secret):

```bash
curl -s -b cookies.txt -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF" -H "Authorization: Bearer $ADMIN_ACCESS" \
  -d '{
    "name": "My Web App",
    "redirect_uris": ["https://app.example.com/callback"],
    "grants": ["authorization_code", "refresh_token"],
    "scopes": ["openid", "profile", "email"],
    "confidential": false
  }' \
  http://localhost:4011/v1/oauth/clients
```

The response is `{ success: true, data: { clientId, clientSecret? } }`
(`clientSecret` is present only for confidential clients). Keep it server-side.
The OpenAPI reference documents these fields as `client_id`/`client_secret`;
the `apps/identity-server` admin console variant (`POST /v1/admin/clients`)
returns `{ client: { clientId, name, redirectUris, grants, scopes, isActive, ... }, clientSecret }`.
For machine-to-machine clients, grant only `client_credentials`.

## 3. Generate PKCE parameters

Public clients must prove ownership of the authorization code with PKCE.
Generate a 43+ character `code_verifier` and its S256 `code_challenge`:

```ts
import { generateCodeVerifier, generateCodeChallenge } from '@pezhwan/oauth';

const codeVerifier = generateCodeVerifier(); // 32 random bytes, base64url
const codeChallenge = generateCodeChallenge(codeVerifier, 'S256'); // SHA-256 → base64url
```

## 4. Authorize (get a code)

The user must already have a session at the identity server. `GET
/v1/oauth/authorize` reads the identity from the bearer token and redirects to
`redirect_uri#code=...&state=...&expires_in=...`:

```text
GET http://localhost:4011/v1/oauth/authorize?client_id=<client_id>
    &redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
    &response_type=code&scope=openid%20profile%20email
    &state=<opaque>&nonce=<opaque>
    &code_challenge=<S256>&code_challenge_method=S256
Authorization: Bearer <accessToken>
```

The endpoint is mounted behind `createAuthenticate` in
`apps/identity-server/src/server.ts` and refuses to redirect to a URI it has
not validated. `demos/oauth-demo/server.ts` shows the equivalent SDK call —
`runtime.oauth.authorizeCode({ ... codeChallenge, codeChallengeMethod: 'S256', authMethod: 'password' })`.

## 5. Exchange the code

`POST /v1/oauth/token` is `application/x-www-form-urlencoded` and returns the
RFC 6749 token response:

```bash
curl -s -X POST http://localhost:4011/v1/oauth/token \
  -d grant_type=authorization_code \
  -d client_id=$CLIENT_ID \
  -d code=$CODE \
  -d redirect_uri=https://app.example.com/callback \
  -d code_verifier=$CODE_VERIFIER
```

```json
{
  "access_token": "<jwt>",
  "token_type": "Bearer",
  "expires_in": 900,
  "refresh_token": "...",
  "id_token": "<jwt>",
  "scope": "openid profile email"
}
```

With `openid` in scope you also receive an `id_token`. Errors use the OAuth
shape: `{ "error": "invalid_grant", "error_description": "..." }`.

## 6. Refresh the access token

The `refresh_token` grant rotates the pair:

```bash
curl -s -X POST http://localhost:4011/v1/oauth/token \
  -d grant_type=refresh_token \
  -d client_id=$CLIENT_ID \
  -d refresh_token=$REFRESH_TOKEN
```

A confidential client authenticates by adding `client_secret` to the form body
(`client_secret_basic` / `client_secret_post` are advertised in discovery).

## 7. Machine-to-machine: client_credentials

Servers authenticate with a confidential client and no user:

```bash
curl -s -X POST http://localhost:4011/v1/oauth/token \
  -d grant_type=client_credentials \
  -d client_id=$CLIENT_ID \
  -d client_secret=$CLIENT_SECRET \
  -d scope=openid
# { "access_token": "<jwt>", "token_type": "Bearer", "expires_in": 900 }
```

These tokens carry a machine `sub` (`client:<clientId>`, `authMethod: 'service'`)
with no user account behind them — see machine-identity handling in
`packages/express/src/index.ts` and the `demos/machine-to-machine/` demo.

## 8. Verify tokens

Access tokens verify against the JWKS:

```ts
import { jwkToPem, verifyIdToken, decodeIdToken } from '@pezhwan/oauth';
// discover → jwks_uri → key for the id_token's `kid` → jwkToPem(jwk)
const claims = await verifyIdToken(idToken, {
  issuer: 'http://localhost:4011',
  audience: clientId,
  nonce: expectedNonce,
  jwksProvider: async () => pem,
});
```

`verifyIdToken` enforces signature, `iss`, `aud`, expiry (with leeway) and
`nonce`. A broken audience or issuer throws. For PEZHWAN-issued access tokens
the express middleware already does this via `runtime.tokens.verifyAccessToken`.

## React: useSSO

For social/SSO-style starters, `useSSO` builds the authorization URL and
redirects — the runtime continues the exchange:

```tsx
import { useSSO, SSOLogin } from '@pezhwan/react';

function LoginButton() {
  const { getAuthorizeUrl, start } = useSSO();
  return <SSOLogin provider="google" redirectUri="https://app.example.com/callback" />;
  // start('google', redirectUri)  → window.location.assign(getAuthorizeUrl(...))
}
```

## Troubleshooting

| Problem                               | Cause / fix                                                                         |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| `401 UNAUTHENTICATED` at authorize    | Caller has no bearer session — the reference server requires an authenticated user. |
| `invalid_request` / no redirect       | `redirect_uri` not registered on the client, or `response_type` not `code`.         |
| `invalid_grant` at exchange           | Code already used (one-time), expired, or `code_verifier` mismatch.                 |
| `INVALID_SCOPE` at authorize          | Requested scope not in the client's registered `scopes`.                            |
| Missing `id_token`                    | `openid` scope omitted.                                                             |
| `client_secret` required              | Client was registered `confidential: true`.                                         |
| Refresh rejects after password change | Refresh session's `tokenVersion` bumped — issue new tokens.                         |
